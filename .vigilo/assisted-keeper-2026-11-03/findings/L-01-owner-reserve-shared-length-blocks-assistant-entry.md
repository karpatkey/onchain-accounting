# L-01 — OWNER_RESERVE bounds the shared length, so a saturated keeper share can still block the Safe's Assistant entry path
Severity: Low (design residual, acknowledged in ADR 0030 S13) | Evidence: POC_VALIDATED (behaviour), impact = availability/under-report only
Location: src/balances/AssistedBalanceAdapters/AssistedCoordCache.sol:303-326 (`_submitFor` limit = cap - OWNER_RESERVE; `_addEntry` checks `_coords[account].length >= limit`); uncaught owner `submit` in EtherFiWithdrawalQueueAssistant.requestWithdraw / StakeWiseV3ExitQueueAssistant.enterExitQueue:59 / NexusMutualStakingPoolsAssistant.depositTo:67.
Scenario: third parties create live dust positions owned by the Safe (requestWithdraw(recipient), enterExitQueue(receiver), depositTo(destination)); a compromised or mis-policied keeper files 224 of them. Once the owner holds 32 of its own entries, the next Assistant entry reverts CoordinateCacheFull, so the Safe's only allow-listed protocol entry is blocked. The only recovery is `evict`, which is not reachable through an Assistant and needs a roles entry or a signer transaction.
PoC: test/vigilo-audit/AssistedKeeperAudit.t.sol::AuditOwnerReserveTest.test_keeperSaturation_ownerKeeps32_then_blocked_until_evict — PASS (keeper stops at 224; owner gets exactly 32; the 33rd owner submit reverts CoordinateCacheFull(safe,256); evict then frees a slot).
No over-report, no fund loss. The keeper cannot remove anything.
Fix (operational, no code needed): before granting SUBMITTER_ROLE, add a roles entry for `evict(bytes)` on each adapter (owner Safe -> adapter, scoped) so recovery doesn't need a signer transaction. Have the keeper alert when an account's headroom drops below OWNER_RESERVE. Optional code change: count keeper-filed entries separately and cap that count at cap - OWNER_RESERVE, so later dead-entry churn on the owner side never shrinks the owner's reserve.
