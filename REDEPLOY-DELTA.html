New proxy required

This is not an implementation upgrade. A new NAVCalculator proxy must be deployed, and the live one at 0x80eD5cc6…afa8d is abandoned in place.

The reason is the least obvious fact in this whole redeploy, and it is not the implementation. An implementation change alone would be a routine UUPS upgrade. The obstacle is ERC20Default: it is minted inside initialize() and pinned by Balances._setErc20DefaultBalanceAdapter, which reverts InvalidArguments() if the address is already set. There is no setter on the current implementation, and NAVRegistryLib.removeBalanceAdapter/removeBalanceAdapters explicitly reject the default-adapter singleton. ERC20DefaultBalanceAdapter.sol did change in this wave (+43 / −11, with BalanceAdapterBase.sol +8 / −3), and it inlines LabelLib, an internal library whose hardening only reaches a contract that is recompiled and redeployed. So the deployed ERC20Default is stale, and with the current implementation and existing admin surface there is no path that repoints it.

Stated as a decision, not an impossibility — because the impossibility version is refutable. This is UUPS, so an upgrade can ship arbitrary new code, including bespoke migration logic that repoints ERC20Default. "Add a setter in the upgrade" is therefore a real option and the first objection a reviewer will raise; a document claiming it cannot be done invites its whole conclusion to be dismissed on that one point.

The accurate claim survives the objection. Repointing means writing, reviewing and auditing one-off migration logic into an upgrade of a live contract holding real value — and at the end of it still deploying a new ERC20Default, since the stale one cannot be fixed in place either way. Set against a fresh proxy, that buys nothing and adds a bespoke, single-use, high-blast-radius code path to the audit surface. Judgement A new proxy is therefore the chosen route on cost and risk, not a forced one.

Both external libraries have moved as well, so new library deployments and a new implementation are required regardless — a moved library forces a new implementation even where the implementation's own source is unchanged, because the libraries are linked by pinned CREATE2 address.

Confirmed by rehearsal The fork rehearsal produced exactly this: a new proxy 0x54EaD2A1…, distinct from the live 0x80eD5cc6…, with a fresh ERC20Default at 0x4Bc39Dce….

The four engineering campaigns

The 63 PRs are not 63 unrelated fixes. Nearly all of the src/ churn belongs to one of four campaigns, and they share a property: each began from a defect that produced a wrong number silently — no revert, no staleness flag, no irregular flag.

Fail-open reads — try/catch does not catch what everyone assumed

The governing discovery: a try/catch does not intercept an ABI-decode failure of the return data. The decode runs in the calling frame, so it reverts past the catch. Worse, a high-level call expecting return data emits no extcodesize pre-check — the returndata-size check subsumes it — so a callee returning zero bytes makes the call succeed and the decode then reverts in the caller.

Why that was dangerous rather than untidy: an adapter wrapped in a per-instance catch looks defended. In practice a malformed reply escaped it, reached the base class, and was scored a benign revert — so the whole instance, including any debt leg, became an empty array. Dropping a debt leg raises reported NAV, the one direction these adapters may never move.

The remedy is uniform: replace typed calls to untrusted addresses with bounded low-level reads that mask rather than revert (StaticCallLib.safeAddr / probeWord), and fail toward omitting one leg rather than an instance.

Gas exhaustion — separating "cannot read" from "ran out of gas"

A fail-open read cannot distinguish those alone, and conflating them turns a starved read into a silent under-report. The new src/utils/GasStipendLib.sol centralises the policy: forward a proportion of the frame (available − available/64), and treat a read as starved at stipend − stipend/8. Proportional rather than fixed matters — a fixed ceiling is unrecoverable by supplying more gas.

Starvation now raises named errors (AdapterGasExhausted, InstanceGasExhausted, CoordinateGasExhausted, RedeemValueGasExhausted), so an operator sees a loud failure rather than a plausible number.

The subtle result worth carrying forward: a nested guard must classify against its own frame, not the stipend it was handed. Classifying against the forwarded stipend leaves a narrow band (ratios ≈0.861 vs 0.875) where a starved read is scored a genuine failure and silently dropped.

Position identity — a broken JOIN with a double-count hazard

Meta-adapters advertise a governed instance set via positionIds() and emit legs carrying a positionId. Those must agree, because downstream reconciliation joins on them. An audit of 21 adapters found exactly one divergence — Aave V3 — and the consequence was a NAV double-count hazard: with two Aave data providers in play, a broken join could attribute the same position twice. IPositionEnumerable was added so the governed set is enumerable on chain rather than inferred, and ProtocolNames.sol gives each adapter a stable protocolName().

Reads that outgrew a single eth_call

A complete NAV read reached roughly 30M gas while NAVCalculator approached the EIP-170 code-size ceiling. Pagination adds getAccountNavForAdapters for slice-wise reads, with the constraint that a partial result must never be mistaken for a whole one — so the partial type does not nest a full NAV. A registered-asset getter removes a full registry re-scan measured at super-linear cost per call.

The pair-identity guard, and what it can and cannot prove

A wrong feed of the right shape is the dangerous case: wiring Base wstETH_L2 to the cbETH/ETH feed yields 1.136 × ETH/USD instead of 1.240 × — a permanent silent under-report with stale = false and irregular = false. RateFeedGuard now runs inside 03_DeployPriceFeeds before anything is constructed, checking two independent properties plus a bound:

  • Pair identity — exact description() match against a per-instance literal in deploy config.
  • Contract-readability — the feed is read from a contract frame. This is the only check that catches the ETHx shape, because there description() was correct on the bad address.
  • Plausibility band — per asset class, catching cross-class confusion (LDO/ETH trades at 0.000192) and forged or absent descriptions.

Neither subsumes the other: the band cannot separate wstETH/ETH (1.2404) from cbETH/ETH (1.1361), and identity cannot detect a feed no contract can read.

Verified on chain All 20 live rate-feed addresses are the correct pair, checked across mainnet, Arbitrum, Base and Gnosis. A separate sweep of all 83 configured Chainlink-shaped addresses (63 proxies, 19 RedStone, 1 raw aggregator) found the ETHx instance to be the only occurrence of that defect.

Judgement That is the argument for a deploy-time gate rather than a one-off correction: the state is clean now, and the gate is what keeps it clean across a redeploy that re-enters every address by hand.

ADR 0019 (NAV-sourced base price) remains the governing design — custom feeds read base/USD from the NAV rather than composing an independent base feed, removing a mixed-feed failure mode. Operational consequences

What a deployer needs, as distinct from what a reviewer needs.

Deploy blocker — resolved The ETHx rate-feed address, and the phantom writes it left behind.

03_DeployPriceFeeds reverted on the ETHx instance, because the constructor's assertChainlinkOracle was denied by the access controller. The damaging part is the aftermath: vm.writeJson side effects are not rolled back when a script reverts, so the aborted run left eighteen phantom customPriceFeeds addresses in the deployment record for contracts that were never deployed — which step 04 then collided with. Fixed, but the failure mode generalises: a reverting deploy script can leave a partially-written record that later steps trust.

Deploy blocker — resolved by #233 ezETHCrossRateMarket could not be deployed at all: 03_DeployPriceFeeds reverted RateFeedGuardMissing("ezETHCrossRateMarket", "yToXFeed").

Two correct changes collided. #216 made the rate-feed guard fail closed — a feed with no rateFeedGuard block is refused rather than waved through — which is the right default and the whole point of the guard. #224 then added ezETHCrossRateMarket without such a block. Neither PR was wrong in isolation; the composition was a hard stop on the deploy.

Why the block could not simply be filled in. The feed is a RedStone Classic-Push feed, and its description() returns the constant string "Redstone Price Feed" — no pair, no asset, identical across every RedStone feed on every pair. An exact-match pair assertion is therefore unimplementable for that whole family, not merely unwritten. #233 declares it: description: "$UNVERIFIABLE" plus a recorded reason, so the pair check is dropped explicitly while the plausibility band and the contract-readability check still apply.

Judgement A declared gap and a silent one look identical in the deployed system and are opposites in review. The alternative — quietly exempting feeds without a guard block — would have restored #216's original defect for every future feed. Narrowing one axis for one documented provider limitation, in config where a reviewer must read it, keeps the guard closed everywhere else.

Required FOUNDRY_PROFILE=slow is mandatory for RegisterAssets — it is not a throughput knob.

[profile.slow] raises both gas_limit and memory_limit from 1 GiB to 16 GiB, and registering the full asset set in one call frame accumulates quadratic EVM memory-expansion cost. Run without it and the step dies with MemoryOOG — a partial registration, which is worse than a clean failure because the NAV then prices only part of the book.

Attribution corrected The knob that actually governs this is gas_limit, not memory_limit. An earlier revision named memory_limit as the cause. That was not merely imprecise — it pointed at the wrong setting, so anyone raising memory_limit alone would have seen the same failure and concluded the profile was irrelevant. Established by controlled experiment, varying one at a time, and it matches foundry.toml's own comment: memory expansion trips MemoryOOG "against the default 1 GiB script gas_limit".

Safe for a deploy — measured Neither setting is a compiler setting, and [profile.slow] was confirmed bytecode-identical to [profile.default] on both pinned libraries. That matters because the profile is used on a broadcasting step: if it altered compilation at all, the deploy would ship different code than the pins were computed against.

Judgement The "19 of 43" figure previously quoted here was an instrument defect, not a limit. rehearse_fork was silently ignoring FOUNDRY_PROFILE=slow and running the step on the default profile, so 19 measured the harness rather than the script. With the profile actually applied, RegisterAssets completes 43 of 43. Recorded because the number was circulating as a property of the deploy, and a deployer who believes the ceiling is 19 will plan around a constraint that does not exist.

Downstream cutover — required Every consumer of the NAV must repoint. A new proxy means anything reading 0x80eD5cc6cEbAe4fEE1eD8687279aa492A50afa8d — kpkShares, the portal, agents, subgraphs — has to be moved to the new address. The old proxy keeps answering, which is the hazard: nothing breaks loudly, consumers simply keep reading a NAV that is no longer maintained. Judgement This is the single largest external consequence of the redeploy, and the only one whose completion is not visible from inside this repository.

Re-registration — required A fresh proxy starts empty. initialize() establishes only ERC20Default, so everything else must be re-established on the new proxy: all registered assets, all price feeds, all plain balance adapters, all meta-adapters, and 110 meta-instance registrations. This is the bulk of the deploy's wall-clock, and it is also where the FOUNDRY_PROFILE=slow requirement below bites.

110, not 113 — an earlier revision of this document said both. 113 counts every meta-adapter in nav-config/meta-balance-adapters/<chain>.json while ignoring enabled. The difference is exactly three disabled adapters carrying one instance each — mainnet BalancerV2PoolsMeta and BalancerV2GaugesMeta, and bsc PancakeSwapV2PoolsMeta. ConfigReader.isAdapterEnabled gates registration and a missing key reads as false, so 06_Configure never registers any of them. 110 + 3 = 113.

Sequencing Pin verification belongs immediately before deployment, against the final tree. The pins are a regenerated artifact; verifying them per-PR against a moving base says little, and repinning mid-stream is how a value becomes stale from birth.

But the deploy is held for the PegKind/AccrualKind work — which may or may not prove deliverable on-chain — so 6e5fa2e9 cannot yet be assumed to be the tree that ships, and this gate must be re-run against whichever tree is.

Judgement Re-run the clean build anyway if any commit lands before broadcasting, and treat a mismatch as "the tree moved", never as "edit the values until it goes green".
