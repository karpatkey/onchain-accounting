# 0010 — Meta balance adapters: one immutable adapter per protocol, instance set held on NAVCalculator

**Status:** accepted

## Context

Until now there is **one deployed balance adapter contract per pool / market / vault**. `MorphoVaultBalanceOracle` pins a single vault in its constructor; `BalancerV3PoolBalanceOracle` pins a single (pool, gauge); `AaveV3InstanceBalanceOracle` pins a single market DataProvider. Covering N Morpho vaults means deploying and registering N immutable contracts, each via CREATE2 + a `06_Configure` Safe TX.

For protocols with many fungible instances (Morpho vaults/markets, Balancer pools, Convex/Aura positions, Aave instances) this scales badly: every new pool is a deploy, an audit-surface delta, and a governance action. The [ADR 0001](0001-balance-adapter-factory-pattern.md) factory pattern was designed to soften this but was never shipped.

The whole oracle stack is being redeployed, which is the window to fix the structure. The question is how to let **one** adapter serve **many** instances without breaking the framework's core rule — *adapters are immutable, no `Ownable`, no admin functions* (see [ADR 0005](0005-aave-safety-module-hardcoded-immutable.md); the sole documented mutable exception is the proof-verified Merkl cache, [ADR 0007](0007-merkl-trust-minimized-cache.md)).

Two routes were considered:

1. **Owner-gated registry inside the adapter.** The adapter holds a mutable set of instances, gated by an `onlyOwner` (Security Council Safe) `addInstance`/`removeInstance`. This is what the original design discussion landed on. It works, but it makes *every* meta-adapter a new mutable, admin-controlled contract — a fresh deviation from ADR 0005 for each protocol, and a standing audit burden.

2. **Instance set held on NAVCalculator; adapter stays immutable and instance-stateless.** The adapter is a pure function of `(account, instance)` over *any* instance of the protocol. The governed "which instances do we actually query" set lives on `NAVCalculator` — which is already UUPS-upgradeable and `AccessControl`-gated (`MANAGER`) — and is passed to the adapter at query time.

## Decision

Adopt route 2. Introduce a second adapter class alongside `IBalanceOracleAdapter`:

- **`IMetaBalanceOracleAdapter`** (`src/balances/IMetaBalanceOracleAdapter.sol`) extends `IBalanceOracleAdapter` and adds two instance-aware methods keyed by a `bytes32` instance coordinate:
  - `getOraclePositionsForInstances(account, bytes32[] instances, assetFilter)`
  - `underlyingAssetsSupportedForInstances(bytes32[] instances)`
  The inherited no-arg balance getters (`getOracleBalances` / `getOracleBalanceForAsset`) return **empty/zero** — they are not on the NAV path. `getOraclePositions(account, assetFilter)` and `underlyingAssetsSupported()` are **not** empty: they read the adapter's NAV-configured instance set (`getMetaInstances(address(this))`) and fan out over it (see next bullet).
- **`MetaBalanceOracle`** (`src/balances/MetaBalanceOracle.sol`) — abstract base providing ERC165 (advertising both interfaces), per-instance fan-out with **per-instance revert isolation** (a bad instance cannot zero out the batch), and the shared registered-asset helper. Concrete adapters implement two hooks: `_instancePositions` and `_instanceAssets`. Its `getOraclePositions(account, assetFilter)` reads its own NAV-configured set via `NAV_CALCULATOR.getMetaInstances(address(this))` and fans out over it.
- **`NAVCalculator` / `Balances`** gain a per-oracle instance registry:
  - `_metaInstances` (a plain `bytes32[]` per oracle) holds the configured set; `getMetaInstances(oracle)` exposes it; `_metaInstanceTotal` is a running count used only to size the NAV read buffer.
  - `setMetaInstances` is gated by the existing `MANAGER` role — the same privilege that already governs `addBalanceOracle`. It applies to any registered oracle; only meta-adapters read the set, so it is inert for others.
  - **The NAVCalculator read path is unchanged**: it calls `getOraclePositions(account, assetFilter)` on every oracle as before. Meta-adapters pull their own set inside that call, so there is no meta-specific branch (and no per-oracle ERC165 flag) in the hot path. This also keeps `NAVCalculator` under the EIP-170 code-size limit, which a routing branch would have exceeded.
- Per-instance identity (`positionId`, `positionDetail`) is **derived on-chain** from the instance coordinate (e.g. `positionId = vaultAddress.toHexString()`, `name` read from the vault's ERC20 `name()`). Nothing instance-specific is stored in config.

All meta-adapter contracts use the `…MetaBalanceAdapter` suffix (the abstract base stays `MetaBalanceOracle` / `IMetaBalanceOracleAdapter`; the per-instance `*BalanceOracle` adapters they supersede keep the repo's existing suffix).

The concrete adapters:
- **`MorphoVaultsMetaBalanceAdapter`** (`src/balances/protocols/MorphoVaultsMeta.sol`): one adapter for *every* Morpho ERC4626 vault. Instance coordinate = vault address (widened to bytes32). Config: `metaInstances` (address array).
- **`MorphoMarketsMetaBalanceAdapter`** (`src/balances/protocols/MorphoMarketsMeta.sol`): one adapter for *every* Morpho Blue market. Instance coordinate = the **`bytes32` marketId, used directly** (the case the bytes32 coordinate was chosen for). Emits up to three gross legs per market (collateral / loan-supply / loan-borrow), matching the per-market `MorphoMarket` adapter. Config: `metaInstancesRaw` (raw bytes32 array). Because a single asset filter can match two legs (loan-token supply + borrow), `NAVCalculator._getPositionBalances` sizes its buffer as `2 * (oracles + metaInstanceTotal) * assetCount` in both the filtered and unfiltered cases (see "NAV read-buffer sizing" below).

- **`AaveV3InstancesMetaBalanceAdapter`** (`src/balances/protocols/AaveV3InstancesMeta.sol`): one adapter for *every* Aave V3 instance (Core, Prime, …). Instance coordinate = the instance's **ProtocolDataProvider address** (widened to bytes32); reserves are enumerated trustlessly inside each instance via `getAllReservesTokens()` (not separate coordinates). Emits up to two legs per reserve (Supply/Collateral + Borrow), matching `AaveV3Instance`. Config: `metaInstances` (address array of DataProviders). Identity derived on-chain: positionId = the instance Pool (`ADDRESSES_PROVIDER.getPool()` — matches the per-instance adapter), name = `ADDRESSES_PROVIDER.getMarketId()`.

- **`BalancerV3PoolsMetaBalanceAdapter`** + **`BalancerV3GaugesMetaBalanceAdapter`** (`src/balances/protocols/balancer/`): the single `BalancerV3PoolBalanceOracle` (which pinned one `(pool, gauge)` and emitted both wallet-LP `Supply` and gauge `Staking`/`Rewards` legs) is **split into two meta-adapters along its two structurally distinct legs**:
  - **Pools** — wallet-held (unstaked) AMM liquidity only. Instance coordinate = the **pool/BPT address** (V3 identifies pools by address; there is no `bytes32` poolId as in V2). Emits one `Supply` leg per underlying pool token. Config: `metaInstances` (pool addresses). Constructor `(protocol, navCalculator)`.
  - **Gauges** — gauge-staked LP + BAL/extra rewards. Instance coordinate = the **gauge address**. Emits one `Staking` leg per underlying pool token (staked BPT share) plus `Rewards` legs (BAL via the minter, extra gauge reward tokens). Config: `metaInstances` (gauge addresses). Constructor `(balancerMinter, protocol, navCalculator)`.
  - The shared pool-share math (`poolBalanceOf`, ERC4626 unwrap) lives in `BalancerV3PoolLib` so both adapters stay leg-for-leg consistent with the original. The only numerical difference: the combined adapter did a single `poolBalanceOf(wallet + staked)` conversion, whereas the split converts wallet and staked separately — a ≤ a-few-units rounding difference per token (fork-tested for parity within tight tolerances).

- **`UniswapV3PoolsMetaBalanceAdapter`** + **`UniswapV2PoolsMetaBalanceAdapter`** (`src/balances/protocols/uniswap/`), with the PancakeSwap forks **`PancakeSwapV3PoolsMetaBalanceAdapter`** / **`PancakeSwapV2PoolsMetaBalanceAdapter`** (`src/balances/protocols/pancakeswap/`): one adapter per family for *all* Uniswap-style pools/pairs. Instance coordinate = the **pool address (V3) / pair address (V2)**.
  - **V3** emits up to four legs (token0/token1 `Supply` from in-range liquidity + token0/token1 `Fees`), scanning the account's NFTs (bounded at 256) filtered by the pool's `(token0, token1, fee)`. The NonfungiblePositionManager is the chain-level constant pinned in the constructor `(positionManager, protocol, navCalculator)`; pools come from `metaInstances`. `slot0` is read via a `virtual _slot0(pool)` hook so the PancakeSwap V3 subclass overrides only that read (PCS's `slot0().feeProtocol` is `uint32`, not Uniswap's `uint8`).
  - **V2** emits one `Supply` leg per token (dilution-adjusted pro-rata reserves); constructor `(protocol, navCalculator)`. The PancakeSwap V2 meta is a thin subclass (byte-for-byte V2 fork; protocol string set per deployment).
  - The read math lives in `UniswapV3PoolLib` / `UniswapV2PairLib` (mirroring `BalancerV3PoolLib`), so each meta-adapter is leg-for-leg identical to the per-instance adapter it supersedes (parity fork-tested, **exact** — no two-conversion rounding). The V3 libs link the GPL-2.0-or-later Uniswap math (`uniswap/lib/*`), so those meta-adapters are GPL combined works (ADR 0008). Identity derived on-chain: positionId = pool/pair address; name = `sym0/sym1 feeTier` (V3) / `sym0/sym1 LP` (V2).

- **`StakeWiseV3VaultsMetaBalanceAdapter`** (`src/balances/protocols/StakeWiseV3VaultsMeta.sol`): one adapter for *every* StakeWise V3 vault. Instance coordinate = the **vault address**. Emits two gross legs per vault — `Staking` (vault shares → underlying via `convertToAssets(getShares)`) and `Borrow` (osToken debt → underlying via `convertToAssets(osTokenPositions)`, `isDebt=true`) — matching the per-vault `StakeWiseV3Vault` adapter. The underlying staking asset (ETH sentinel on mainnet, GNO on Gnosis) is the chain-level constant pinned in the constructor `(underlyingToken, protocol, navCalculator)`; vaults come from `metaInstances`. Identity derived on-chain: positionId = vault address; name = vault `name()`. The per-vault adapter's signed-net convenience getters are dropped (not on the NAV path).

- **`GearboxMarketsMetaBalanceAdapter`** (`src/balances/protocols/GearboxMarketsMeta.sol`): one adapter for *every* Gearbox V3 ERC4626 farming pool. Instance coordinate = the **market address**. Emits one `Supply` leg (`convertToAssets(balanceOf)`) in the pool's underlying, matching the per-market `GearboxMarket` adapter. Constructor `(protocol, navCalculator)`. Identity derived on-chain: positionId = market address; name = market `name()`.

- **`CompoundV3CometsMetaBalanceAdapter`** (`src/balances/protocols/CompoundV3CometsMeta.sol`): one adapter for *every* Compound V3 (Comet) market. Instance coordinate = the **comet address**. Emits the base `Supply`/`Borrow` leg, a `Collateral` leg per collateral, and a COMP `Rewards` leg — matching the per-comet `CompoundV3Comet` adapter (multi-role assets such as COMP-as-collateral-and-reward emit one leg per role). The CometRewards contract and reward token (COMP) are the chain-level constants pinned in the constructor `(compoundRewards, rewardToken, protocol, navCalculator)`; comets come from `metaInstances`. The base-accrual, reward-accrual, and per-comet collateral enumeration are delegated to `CompoundV3CometLib` (the per-comet adapter snapshotted collaterals + the accrual descale factor at construction; the library derives them per call). Identity derived on-chain: positionId = comet address; name = comet `name()`.

- **`FluidFTokensMetaBalanceAdapter`** + **`FluidVaultsMetaBalanceAdapter`** (`src/balances/protocols/Fluid{FTokens,Vaults}Meta.sol`): the two Fluid families. **fTokens** are ERC4626 lending vaults — instance coordinate = fToken address; one `Supply` leg (`convertToAssets(balanceOf)`); constructor `(protocol, navCalculator)`. **T1 vaults** report collateral + debt — instance coordinate = vault address; a `Collateral` + `Borrow` leg aggregated over the account's NFT positions (via the resolver); the VaultResolver is the chain-level constant pinned in the constructor `(vaultResolver, protocol, navCalculator)`. The vault read logic (tokens via `constantsView`, NFT aggregation with the static-prefix decode) is delegated to `FluidVaultLib`, mirroring the per-vault `FluidVault` adapter. Identity derived on-chain: fToken positionId/name = fToken address / `symbol()`; vault positionId/name = vault address / `collSym/debtSym`. T1 vaults only.

These migrate their per-instance predecessors (`MorphoVault_*`, `MorphoMarket_*`, `AaveV3_*`, `BalancerV3_*`, `UniswapV3_*`, `StakeWiseV3Vault_*`, `GearboxMarket_*`, `CompoundV3_*` (mainnet), `Fluid_fToken_*`/`Fluid_Vault_*` (mainnet), and the disabled PancakeSwap entries) in the chain configs + integration suite; NAV value is unchanged for the address/marketId-keyed adapters (verified: position-level delta = 0) and within sub-unit rounding for the Balancer split. The derived on-chain names differ cosmetically from the old config strings (snapshot-only, not NAV).

**NAV read-buffer sizing.** `NAVCalculator._getPositionBalances` sizes its temp buffer as `2 * (totalOracles + _metaInstanceTotal) * getAssetCount()`. The `2×` factor covers adapters that emit two legs for the same asset within one instance (lending supply+borrow on a reserve; a Morpho market's loan-token supply+borrow; a Uniswap V3 pool's per-token Supply+Fees); the `+ _metaInstanceTotal` term gives every configured meta-instance the same per-instance budget the single per-instance oracle it replaces received. Sized identically in the filtered and unfiltered cases.

## Consequences

- **Adapters stay immutable.** No `Ownable`, no admin functions, no per-protocol ADR-0005 deviation. The mutable, governed state lives where mutable governed state already lives — the upgradeable, role-gated `NAVCalculator`. This is the key advantage over route 1.
- **Adding a pool/vault is a `MANAGER` TX, not a deploy.** `setMetaInstances(adapter, [...])` instead of CREATE2 + register.
- **Trust model.** `MANAGER` can add an arbitrary instance coordinate. A malicious/incorrect instance can only mis-report through the adapter's own read path (e.g. a fake ERC4626 that lies about `convertToAssets`); it cannot fabricate values out of band, and NAV still drops positions whose asset is unregistered. Instance curation is therefore a governance responsibility (index → whitelist → `MANAGER` TX), mirroring how price feeds and oracles are already added.
- **Gas / sizing.** A meta-adapter can emit up to `2 * instances * assets` positions, so `NAVCalculator._getPositionBalances` sizes its buffer as `2 * (totalOracles + _metaInstanceTotal) * getAssetCount()` (see "NAV read-buffer sizing"). Per-instance reverts are isolated via an external self-call wrapped in try/catch.
- **Migration.** This PR migrates the mainnet Morpho vaults, Morpho markets, Aave V3 instances, Balancer pools/gauges, and Uniswap V3 pools to their meta-adapters (the superseded per-instance entries are set `enabled: false` in chain config; their contracts remain in the tree). The disabled PancakeSwap entries are migrated on BSC/Base. The per-instance adapter contracts themselves are untouched. `bytes32` was chosen for the instance coordinate so the same interface serves address-keyed protocols (vaults, pools, Aave instances) and bytes32-keyed ones (Morpho market ids).
