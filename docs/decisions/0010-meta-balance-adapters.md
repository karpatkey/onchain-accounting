# 0010 — Meta balance adapters: one immutable adapter per protocol, instance set held on NAVCalculator

**Status:** accepted

## Context

Until now there is **one deployed balance adapter contract per pool / market / vault**. `MorphoVaultBalanceAdapter` pins a single vault in its constructor; `BalancerV3PoolBalanceAdapter` pins a single (pool, gauge); `AaveV3InstanceBalanceAdapter` pins a single market DataProvider. Covering N Morpho vaults means deploying and registering N immutable contracts, each via a CREATE deploy + a `06_Configure` registration TX.

For protocols with many fungible instances (Morpho vaults/markets, Balancer pools, Convex/Aura positions, Aave instances) this scales badly: every new pool is a deploy, an audit-surface delta, and a governance action. The [ADR 0001](0001-balance-adapter-factory-pattern.md) factory pattern was designed to soften this but was never shipped.

The whole adapter stack is being redeployed, which is the window to fix the structure. The question is how to let **one** adapter serve **many** instances without breaking the framework's core rule — *adapters are immutable, no `Ownable`, no admin functions* (see [ADR 0005](0005-aave-safety-module-hardcoded-immutable.md); the sole documented mutable exception is the proof-verified Merkl cache, [ADR 0007](0007-merkl-trust-minimized-cache.md)).

Two routes were considered:

1. **Owner-gated registry inside the adapter.** The adapter holds a mutable set of instances, gated by an `onlyOwner` (Security Council Safe) `addInstance`/`removeInstance`. This is what the original design discussion landed on. It works, but it makes *every* meta-adapter a new mutable, admin-controlled contract — a fresh deviation from ADR 0005 for each protocol, and a standing audit burden.

2. **Instance set held on NAVCalculator; adapter stays immutable and instance-stateless.** The adapter is a pure function of `(account, instance)` over *any* instance of the protocol. The governed "which instances do we actually query" set lives on `NAVCalculator` — which is already UUPS-upgradeable and `AccessControl`-gated (`MANAGER`) — and is passed to the adapter at query time.

## Decision

Adopt route 2. Introduce a second adapter class alongside `IBalanceAdapter`:

- **`IMetaBalanceAdapter`** (`src/balances/IMetaBalanceAdapter.sol`) extends `IBalanceAdapter` and adds two instance-aware methods keyed by a `bytes32` instance coordinate:
  - `getAdapterPositionsForInstances(account, bytes32[] instances, assetFilter)`
  - `underlyingAssetsSupportedForInstances(bytes32[] instances)`
  The inherited no-arg balance getters (`getAdapterBalances` / `getAdapterBalanceForAsset`) return **empty/zero** — they are not on the NAV path. `getAdapterPositions(account, assetFilter)` and `underlyingAssetsSupported()` are **not** empty: they read the adapter's NAV-configured instance set (`getMetaInstances(address(this))`) and fan out over it (see next bullet).
- **`MetaBalanceAdapter`** (`src/balances/MetaBalanceAdapter.sol`) — abstract base providing ERC165 (advertising `IMetaBalanceAdapter`, `IBalanceAdapter`, `IPositionDescribable`, and `IERC165`), per-instance fan-out with **per-instance revert isolation** (a bad instance cannot zero out the batch), and the shared registered-asset helper. Concrete adapters implement two required hooks (`_instancePositions` and `_instanceAssets`) and one optional hook (`_instancePositionId(bytes32 instance)` — override to customise positionId encoding; default is `abi.encode(_toAddress(instance))`; override with `abi.encode(instance)` for raw-bytes32 coordinates such as Morpho marketIds and Balancer V2 poolIds). All meta-adapters also implement `IPositionDescribable`: `protocolName()` returns the protocol name set at construction; `describePosition(bytes positionId)` derives a human-readable label from on-chain reads (ERC20 symbols, vault/pool names, pool composition). Its `getAdapterPositions(account, assetFilter)` reads its own NAV-configured set via `NAV_CALCULATOR.getMetaInstances(address(this))` and fans out over it.
- **`NAVCalculator` / `Balances`** gain a per-adapter instance registry:
  - `_metaInstances` (a plain `bytes32[]` per adapter) holds the configured set; `getMetaInstances(adapter)` exposes it; `_metaInstanceTotal` is a running count used only to size the NAV read buffer.
  - A meta-adapter is registered with `addMetaBalanceAdapter(adapter, instances)`, which registers the adapter and seeds its instance set atomically (plain adapters use `addBalanceAdapters` and have no set). `addMetaInstances`/`removeMetaInstances` then mutate an already-registered adapter's set. All are gated by the existing `MANAGER` role — the same privilege that already governs `addBalanceAdapters`. The instance set applies to any registered adapter; only meta-adapters read it, so it is inert for others.
  - **The NAVCalculator read path is unchanged**: it calls `getAdapterPositions(account, assetFilter)` on every adapter as before. Meta-adapters pull their own set inside that call, so there is no meta-specific branch (and no per-adapter ERC165 flag) in the hot path. This also keeps `NAVCalculator` under the EIP-170 code-size limit, which a routing branch would have exceeded.
- Per-instance identity (`protocolId`, `positionId`, `positionKind`) is **derived on-chain** from the instance coordinate (e.g. `positionId = abi.encode(vaultAddress)`, `describePosition()` reads the vault's ERC20 `name()`). Nothing instance-specific is stored in config.

All meta-adapter contracts use the `…MetaBalanceAdapter` suffix (the abstract base stays `MetaBalanceAdapter` / `IMetaBalanceAdapter`; the per-instance `*BalanceAdapter` adapters they supersede keep the repo's existing suffix).

The concrete adapters:
- **`MorphoVaultsMetaBalanceAdapter`** (`src/balances/protocols/MorphoVaultsMeta.sol`): one adapter for *every* Morpho ERC4626 vault. Instance coordinate = vault address (widened to bytes32). Config: `instances` (address array, in nav-config/meta-balance-adapters).
- **`MorphoMarketsMetaBalanceAdapter`** (`src/balances/protocols/MorphoMarketsMeta.sol`): one adapter for *every* Morpho market. Instance coordinate = the **`bytes32` marketId, used directly** (the case the bytes32 coordinate was chosen for). Emits up to three gross legs per market (collateral / loan-supply / loan-borrow), matching the per-market `MorphoMarket` adapter. Config: `instancesRaw` (raw bytes32 array). Because a single asset filter can match two legs (loan-token supply + borrow), `NAVCalculator._getPositionBalances` sizes its buffer as `2 * (adapters + metaInstanceTotal) * assetCount` in both the filtered and unfiltered cases (see "NAV read-buffer sizing" below).

- **`AaveV3InstancesMetaBalanceAdapter`** (`src/balances/protocols/AaveV3InstancesMeta.sol`): one adapter for *every* Aave V3 instance (Core, Prime, …). Instance coordinate = the instance's **ProtocolDataProvider address** (widened to bytes32); reserves are enumerated trustlessly inside each instance via `getAllReservesTokens()` (not separate coordinates). Emits up to two legs per reserve (Supply/Collateral + Borrow), matching `AaveV3Instance`. Config: `instances` (address array, in nav-config/meta-balance-adapters; DataProviders). Identity derived on-chain: positionId = `abi.encode(pool, asset)` per reserve (pool resolved via `ADDRESSES_PROVIDER.getPool()` — matches the per-instance adapter), name = `ADDRESSES_PROVIDER.getMarketId()`.

- **`BalancerV3PoolsMetaBalanceAdapter`** + **`BalancerV3GaugesMetaBalanceAdapter`** (`src/balances/protocols/balancer/`): the single `BalancerV3PoolBalanceAdapter` (which pinned one `(pool, gauge)` and emitted both wallet-LP `Supplied` and gauge `Staking`/`Rewards` legs) is **split into two meta-adapters along its two structurally distinct legs**:
  - **Pools** — wallet-held (unstaked) AMM liquidity only. Instance coordinate = the **pool/BPT address** (V3 identifies pools by address; there is no `bytes32` poolId as in V2). Emits one `Supplied` leg per underlying pool token. Config: `instances` (address array, in nav-config/meta-balance-adapters; pool addresses). Constructor `(protocol, navCalculator)`.
  - **Gauges** — gauge-staked LP + BAL/extra rewards. Instance coordinate = the **gauge address**. Emits one `Staking` leg per underlying pool token (staked BPT share) plus `Rewards` legs (BAL via the minter, extra gauge reward tokens). Config: `instances` (address array, in nav-config/meta-balance-adapters; gauge addresses). Constructor `(balancerMinter, protocol, navCalculator)`.
  - The shared pool-share math (`poolBalanceOf`, ERC4626 unwrap) lives in `BalancerV3PoolLib` so both adapters stay leg-for-leg consistent with the original. The only numerical difference: the combined adapter did a single `poolBalanceOf(wallet + staked)` conversion, whereas the split converts wallet and staked separately — a ≤ a-few-units rounding difference per token (fork-tested for parity within tight tolerances).

- **`UniswapV3PoolsMetaBalanceAdapter`** + **`UniswapV2PoolsMetaBalanceAdapter`** (`src/balances/protocols/uniswap/`), with the PancakeSwap forks **`PancakeSwapV3PoolsMetaBalanceAdapter`** / **`PancakeSwapV2PoolsMetaBalanceAdapter`** (`src/balances/protocols/pancakeswap/`): one adapter per family for *all* Uniswap-style pools/pairs. Instance coordinate = the **pool address (V3) / pair address (V2)**.
  - **V3** emits up to four legs (token0/token1 `Supplied` from in-range liquidity + token0/token1 `Fees`), scanning the account's NFTs (bounded at 256) filtered by the pool's `(token0, token1, fee)`. The NonfungiblePositionManager is the chain-level constant pinned in the constructor `(positionManager, protocol, navCalculator)`; pools come from `instances` (in nav-config/meta-balance-adapters). `slot0` is read via a `virtual _slot0(pool)` hook so the PancakeSwap V3 subclass overrides only that read (PCS's `slot0().feeProtocol` is `uint32`, not Uniswap's `uint8`).
  - **V2** emits one `Supplied` leg per token (dilution-adjusted pro-rata reserves); constructor `(protocol, navCalculator)`. The PancakeSwap V2 meta is a thin subclass (byte-for-byte V2 fork; protocol string set per deployment).
  - The read math lives in `UniswapV3PoolLib` / `UniswapV2PairLib` (mirroring `BalancerV3PoolLib`), so each meta-adapter is leg-for-leg identical to the per-instance adapter it supersedes (parity fork-tested, **exact** — no two-conversion rounding). The V3 libs link the GPL-2.0-or-later Uniswap math (`uniswap/lib/*`), so those meta-adapters are GPL combined works (ADR 0008). Identity derived on-chain: positionId = `abi.encode(npm, tokenId)` per NFT, name = `NFT #<tokenId>` (V3); positionId = pair address, name = `sym0/sym1 LP` (V2).

- **`StakeWiseV3VaultsMetaBalanceAdapter`** (`src/balances/protocols/StakeWiseV3VaultsMeta.sol`): one adapter for *every* StakeWise V3 vault. Instance coordinate = the **vault address**. Emits two gross legs per vault — `Staking` (vault shares → underlying via `convertToAssets(getShares)`) and `Borrowed` (osToken debt → underlying via `convertToAssets(osTokenPositions)`, `isDebt=true`) — matching the per-vault `StakeWiseV3Vault` adapter. The underlying staking asset (ETH sentinel on mainnet, GNO on Gnosis) is the chain-level constant pinned in the constructor `(underlyingToken, protocol, navCalculator)`; vaults come from `instances` (in nav-config/meta-balance-adapters). Identity derived on-chain: positionId = vault address; name = vault `name()`. The per-vault adapter's signed-net convenience getters are dropped (not on the NAV path).

- **`GearboxMarketsMetaBalanceAdapter`** (`src/balances/protocols/GearboxMarketsMeta.sol`): one adapter for *every* Gearbox V3 ERC4626 farming pool. Instance coordinate = the **market address**. Emits one `Supplied` leg (`convertToAssets(balanceOf)`) in the pool's underlying, matching the per-market `GearboxMarket` adapter. Constructor `(protocol, navCalculator)`. Identity derived on-chain: positionId = market address; name = market `name()`.

- **`CompoundV3CometsMetaBalanceAdapter`** (`src/balances/protocols/CompoundV3CometsMeta.sol`): one adapter for *every* Compound V3 (Comet) market. Instance coordinate = the **comet address**. Emits the base `Supplied`/`Borrowed` leg, a `Collateral` leg per collateral, and a COMP `Rewards` leg — matching the per-comet `CompoundV3Comet` adapter (multi-role assets such as COMP-as-collateral-and-reward emit one leg per role). The CometRewards contract and reward token (COMP) are the chain-level constants pinned in the constructor `(compoundRewards, rewardToken, protocol, navCalculator)`; comets come from `instances` (in nav-config/meta-balance-adapters). The base-accrual, reward-accrual, and per-comet collateral enumeration are delegated to `CompoundV3CometLib` (the per-comet adapter snapshotted collaterals + the accrual descale factor at construction; the library derives them per call). Identity derived on-chain: positionId = comet address; name = comet `name()`.

- **`FluidFTokensMetaBalanceAdapter`** + **`FluidVaultsMetaBalanceAdapter`** (`src/balances/protocols/Fluid{FTokens,Vaults}Meta.sol`): the two Fluid families. **fTokens** are ERC4626 lending vaults — instance coordinate = fToken address; one `Supplied` leg (`convertToAssets(balanceOf)`); constructor `(protocol, navCalculator)`. **T1 vaults** report collateral + debt — instance coordinate = vault address; a `Collateral` + `Borrowed` leg aggregated over the account's NFT positions (via the resolver); the VaultResolver is the chain-level constant pinned in the constructor `(vaultResolver, protocol, navCalculator)`. The vault read logic (tokens via `constantsView`, NFT aggregation with the static-prefix decode) is delegated to `FluidVaultLib`, mirroring the per-vault `FluidVault` adapter. Identity derived on-chain: fToken positionId/name = fToken address / `symbol()`; vault positionId/name = vault address / `collSym/debtSym`. T1 vaults only.

- **`AaveV2InstancesMetaBalanceAdapter`** (`src/balances/protocols/AaveV2InstancesMeta.sol`): one adapter for *every* Aave V2 instance. Aave V2's `AaveProtocolDataProvider` shares the `getAllReservesTokens()`/`getUserReserveData()` ABI with V3, so this is a **thin subclass of the V3 instances meta-adapter** — the only override is the pool getter (`_poolOf`), which for V2 resolves via the `LendingPoolAddressesProvider`'s `getLendingPool()` rather than V3's `getPool()` (for the on-chain `positionId`). Same legs as V3 (Supply/Collateral + Borrow per reserve; stable debt not reported). Constructor `(protocol, navCalculator)`. `_poolOf` was lifted to `internal virtual` on the V3 meta to enable this.

- **`BalancerV2PoolsMetaBalanceAdapter`** + **`BalancerV2GaugesMetaBalanceAdapter`** (`src/balances/protocols/balancer/`): the Balancer V2 analogue of the V3 split, but keyed by V2's identifier model. Balancer V2 holds all pool tokens in a single **Vault** (`getPoolTokens(bytes32 poolId)`) and identifies pools by a `bytes32` **poolId** (the BPT address is its top 160 bits) rather than by address.
  - **Pools** — wallet-held (unstaked) liquidity. Instance coordinate = the **raw 32-byte poolId, used directly** (config: `instancesRaw`, since the coordinate is not an address). Emits one `Supplied` leg per underlying pool token (pro-rata of the Vault balances by wallet BPT / supply). The composable-stable BPT-in-pool token is excluded, and supply is read via `getActualSupply()` when present (composable-stable) else `totalSupply()` (legacy weighted/stable). Constructor `(vault, protocol, navCalculator)`.
  - **Gauges** — gauge-staked LP + BAL/extra rewards. Instance coordinate = the **gauge address**. The BPT and its poolId are read on-chain (`gauge.lp_token()` / `getPoolId()`), then the staked share is decomposed via the same Vault-balance math. Emits one `Staking` leg per underlying pool token plus `Rewards` legs. Constructor `(vault, balancerMinter, protocol, navCalculator)`.
  - The pool-share math lives in `BalancerV2PoolLib` (BPT-address derivation, effective supply, Vault pro-rata). Balancer V2 and V3 share the same liquidity-gauge + `BalancerMinter` design, so the BAL inflation math is **identical** to `BalancerV3GaugesMeta` (reused verbatim, real-staker fork-tested there). Unlike the V3 split there is no per-instance V2 predecessor in this repo, so the fork tests assert self-consistency against live Vault reads (exact) rather than parity.

These migrate their per-instance predecessors (`MorphoVault_*`, `MorphoMarket_*`, `AaveV3_*`, `AaveV2_*`, `BalancerV3_*`, `UniswapV3_*`, `StakeWiseV3Vault_*`, `GearboxMarket_*`, `CompoundV3_*` (mainnet), `Fluid_fToken_*`/`Fluid_Vault_*` (mainnet), and the disabled PancakeSwap entries) in the chain configs + integration suite; NAV value is unchanged for the address/marketId-keyed adapters (verified: position-level delta = 0) and within sub-unit rounding for the Balancer split. The derived on-chain names differ cosmetically from the old config strings (snapshot-only, not NAV).

**NAV read-buffer sizing.** The position scan (`PriceFeedLib._getPositionBalances`, fed `getAllAdapters()` / `_metaInstanceTotal` / `getAssetCount()` from `NAVCalculator` — see the EIP-170 note below) sizes its temp buffer as `2 * (totalAdapters + _metaInstanceTotal) * getAssetCount()`. The `2×` factor covers adapters that emit two legs for the same asset within one instance (lending supply+borrow on a reserve; a Morpho market's loan-token supply+borrow; a Uniswap V3 pool's per-token Supply+Fees); the `+ _metaInstanceTotal` term gives every configured meta-instance the same per-instance budget the single per-instance adapter it replaces received. Sized identically in the filtered and unfiltered cases.

## Consequences

- **Adapters stay immutable.** No `Ownable`, no admin functions, no per-protocol ADR-0005 deviation. The mutable, governed state lives where mutable governed state already lives — the upgradeable, role-gated `NAVCalculator`. This is the key advantage over route 1.
- **Adding a pool/vault is a `MANAGER` TX, not a deploy.** `addMetaInstances(adapter, [...])` instead of a CREATE deploy + register.
- **Trust model.** `MANAGER` can add an arbitrary instance coordinate. A malicious/incorrect instance can only mis-report through the adapter's own read path (e.g. a fake ERC4626 that lies about `convertToAssets`); it cannot fabricate values out of band, and NAV still drops positions whose asset is unregistered. Instance curation is therefore a governance responsibility (index → whitelist → `MANAGER` TX), mirroring how price feeds and adapters are already added.
- **Gas / sizing.** A meta-adapter can emit up to `2 * instances * assets` positions, so the position scan (`PriceFeedLib._getPositionBalances`) sizes its buffer as `2 * (totalAdapters + _metaInstanceTotal) * getAssetCount()` (see "NAV read-buffer sizing"). Per-instance reverts are isolated via an external call wrapped in try/catch.
- **Migration.** This PR migrates the mainnet Morpho vaults, Morpho markets, Aave V3 instances, Balancer pools/gauges, and Uniswap V3 pools to their meta-adapters (the superseded per-instance entries are set `enabled: false` in chain config; their contracts remain in the tree). The disabled PancakeSwap entries are migrated on BSC/Base. The per-instance adapter contracts themselves are untouched. `bytes32` was chosen for the instance coordinate so the same interface serves address-keyed protocols (vaults, pools, Aave instances) and bytes32-keyed ones (Morpho market ids).

- **EIP-170 / `NavRegistryLib`.** The cumulative meta-instance machinery (the `addMetaInstances`/`removeMetaInstances` registry, buffer-sizing, per-instance read path) pushed `NAVCalculator` past the 24,576-byte runtime limit. To recover headroom we extracted the registry **storage mutations** — `registerAsset`/`unregisterAsset` (asset registry) and `addBalanceAdapter`/`removeBalanceAdapter` (adapter registry) — into a new external `NavRegistryLib`, DELEGATECALL'd from `NAVCalculator`/`Balances` via `storage`-reference parameters, exactly mirroring the existing `PriceFeedLib` pattern (pre-linked at a deterministic CREATE2 address in `foundry.toml`, deployed by `01_2`/`01` before `NAVCalculator`). Only no-return mutations were moved (cheap call boundary); the trivial getters and the running counts / event emission stay inline. This dropped `NAVCalculator` from ~24,792 to ~23,888 bytes (≈690 B margin) with NAV output unchanged (integration 2/2).

  - **Update (PR #73): the read/compute engine was extracted too.** NAV crept back to the 24,576-byte ceiling (24,537 on main, 39 B margin), and `via_ir` whole-program codegen meant *any* new balance adapter could tip it over even without touching NAV (the Euler adapter did — +280 B from its mere presence in the build). The original "do **not** extract the pricing/enrichment path" reasoning held only for *piecemeal* helper extraction — returning a `Position` (or passing a `PositionBalance`) across the library boundary per call costs more ABI encode/decode bytecode than the inlined body saves (measured: `enrichPositionWithPricing` alone +517 B, `priceConversion` alone +79 B). The fix is to move **whole pipelines** — `computeNav` / `computeAccountPositions` / `hasPositions` / `getAssetsWithPositions` / `healthCheck` / `calculateValue` / `getPriceData` — into `PriceFeedLib`, so the heavy `PositionBalance[]`/`Position[]` arrays are built **and** consumed inside the library and never cross the ABI boundary; `NAVCalculator` keeps only storage, admin mutations, and thin view wrappers. (`optimizer_runs` was ruled out as a lever: even runs=1 only saved 219 B and raises gas system-wide.) This dropped `NAVCalculator` to **21,403 bytes (≈3,173 B margin)**, NAV output unchanged (full unit + NAV/Morpho/Aave fork + integration suites green). `PriceFeedLib`'s pin in `foundry.toml` was regenerated for the new bytecode.
