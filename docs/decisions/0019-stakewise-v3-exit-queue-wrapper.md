# 0019 — StakeWise V3 exit-queue wrapper-fed adapter (delegatecall feeder, self-submit)

Status: accepted

## Context

StakeWise V3 exit-queue positions are not enumerable: a position is identified only by a `positionTicket` emitted in `ExitQueueEntered`, with no owner→tickets view, so a pure-view adapter cannot discover them. ADR [0014](0014-agent-fed-cache-adapters-for-exit-queues.md) surfaces them to NAV with `StakeWiseV3ExitQueueAssistedBalanceAdapter`, fed by an **off-chain** `ASSISTANT_ROLE` agent that scrapes the events and submits `(vault, positionTicket, timestamp)` tuples — leaving a staleness window between the on-chain enter/exit and the agent's next submission.

ADR [0018](0018-wrapper-fed-assisted-balance-adapters.md) added a **wrapper-fed** variant to the assisted family (ADR [0015](0015-assisted-balance-adapter-family.md)): an on-chain wrapper holding `WRAPPER_ROLE` pushes/pops coordinates atomically as it forwards deposits/withdrawals. Its first member (Nexus Mutual staking) uses a **normally-called** wrapper: it `transferFrom`s the depositor's (transferable) NXM, forwards to the pool, and Nexus's **permissionless** `withdraw` routes funds to the NFT owner — so one shared wrapper contract can hold `WRAPPER_ROLE` and act for every depositor.

**StakeWise does not fit that shape.** Two protocol constraints break the normally-called model:

1. `claimExitedAssets(positionTicket, timestamp, exitQueueIndex)` is keyed on `msg.sender` — only the address that was the `receiver` at `enterExitQueue` time can claim. A shared wrapper called normally would be `msg.sender`, so only it could claim; the depositor could not.
2. StakeWise V3 vault shares are internal, non-transferable balances — a wrapper cannot `transferFrom` a depositor's shares to enter the queue on its behalf.

## Decision

Feed the StakeWise exit-queue adapter through a **delegatecall** wrapper that fans its adapter writes through a **self-call**, so the adapter is gated by a single-wrapper `WRAPPER_ROLE` (as in ADR 0018) while the depositor allowlist lives on the wrapper. Same family invariant as ADR 0015/0018 (cache coordinates only, value live, re-verify ownership per read → the feeder can only under-report).

- **`StakeWiseV3ExitQueueWrapper`** (`src/balances/wrappers/`) — a **delegatecall action** contract the depositor Safe delegatecalls. Because it runs in the Safe's context, `address(this)` is the Safe: the vault sees `msg.sender = Safe`, the exit position is owned by the Safe (`receiver` is forced to `address(this)`), the Safe can later claim, and claimed assets are paid directly to the Safe — no custody or asset-forwarding logic. `enterExitQueue(vault, shares)` calls the vault (forcing `receiver = address(this)`, so the `receiver` param is dropped); `claimExitedAssets(vault, positionTicket, timestamp, exitQueueIndex)` claims. Signatures mirror the vault's, with `vault` prepended.
  - **Feeding the adapter via a self-call.** The delegatecalled entrypoints do NOT call the adapter directly (that call would carry `msg.sender = the Safe`, forcing the adapter to grant `WRAPPER_ROLE` to every depositor). Instead they call **back into the singleton** — `StakeWiseV3ExitQueueWrapper(SELF).submit(...)` / `.remove(...)` — which run in the singleton's context and forward to the adapter, so the adapter sees `msg.sender = the singleton`. `submit`/`remove` are `onlyRole(DEPOSITOR_ROLE)` and track the caller (`msg.sender`), so a depositor can only track its OWN tickets; they may also be called standalone by an approved depositor.
  - **Delegatecall consequences, handled:** the delegatecalled entrypoints perform **no storage writes** (a write would corrupt Safe storage), and their `DEPOSITOR_ROLE` gate cannot use the inherited `onlyRole` (that reads Safe storage). Instead they check the role against the wrapper **singleton's own** storage via an immutable `SELF` (`IAccessControl(SELF).hasRole(DEPOSITOR_ROLE, address(this))`). The `submit`/`remove` self-call functions run on the singleton, so they use the normal `onlyRole`. Admins grant/revoke `DEPOSITOR_ROLE` by calling the singleton directly.
- **`StakeWiseV3ExitQueueAssistedBalanceAdapter`** (`src/balances/AssistedBalanceAdapters/`) — **replaces** the ADR-0014 agent-fed adapter of the same name (which is removed; the `ASSISTANT_ROLE`/`submitPositions` off-chain-agent surface is gone). Extends `AccessControl` with a `WRAPPER_ROLE` **granted only to the wrapper singleton** (never to depositors); `submit(account, vault, positionTicket, timestamp)` / `remove(...)` are `onlyRole(WRAPPER_ROLE)`, fed one ticket at a time. It trusts a single feeder (the wrapper), which enforces the depositor allowlist + `account` scoping. The cache + live valuation are unchanged from the prior agent-fed adapter (per-ticket claimable/locked split on `EXIT_CLAIM_DELAY`, live ownership re-verification via `calculateExitedAssets(account, …)`, `positionId = abi.encode(vault)`, `positionInstanceId = bytes32(positionTicket)`, `["Exit Queue", "<receiptSymbol>"]` labels). Kept as a **single self-contained contract** for now; may be abstracted into a shared base in a follow-up.

**Relationship to `WrapperFedBalanceAdapter` (ADR 0018).** This adapter uses the same shape as ADR 0018's framework — a single-wrapper `WRAPPER_ROLE` feeder, incremental submit/remove — but does not depend on that (unmerged) base (this PR is independent on main). The StakeWise-specific twist is the **delegatecall + self-call** indirection: StakeWise keys claim on `msg.sender` and vault shares are non-transferable, so the wrapper must run in the Safe's context (delegatecall), which is why it feeds the adapter via a call back into the singleton rather than directly.

## Consequences

- StakeWise exit-queue tracking moves to an on-chain, atomically-maintained path for managed Safes. The ADR-0014 agent-fed StakeWise adapter is **removed and replaced** by this wrapper-fed adapter (same contract name, `StakeWiseV3ExitQueueAssistedBalanceAdapter`). ADR 0014 still governs its ether.fi sibling.
- The depositor→ticket attribution is enforced on-chain and atomically by the wrapper (its `submit`/`remove` track the caller `msg.sender`, the executing Safe), and every read re-verifies ownership against `receiver = account`, so a faulty depositor can only under-report. The adapter trusts a single address (the wrapper singleton via `WRAPPER_ROLE`); depositors never hold a role on the adapter.
- The wrapper is a documented immutability exception (assisted family), expressed through the adapter's `WRAPPER_ROLE`. Its `enterExitQueue`/`claimExitedAssets` are **delegatecall-only** by design; a direct call would set `receiver = the singleton` and revert (the singleton holds no vault shares).
- Deploy-script / config-JSON wiring is deferred to a follow-up (as for ADR 0018's first member).
- This extends ADR 0015/0018 with a delegatecall + self-call feeder topology, and supersedes the StakeWise V3 portion of ADR 0014 (its ether.fi portion is unaffected).
