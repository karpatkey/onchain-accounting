# 0020 — Wrapper-fed ether.fi withdrawal-queue adapter (`WRAPPER_ROLE`, delegatecalled wrapper)

Status: accepted

## Context

The assisted balance-adapter family (ADR [0015](0015-assisted-balance-adapter-family.md)) covers adapters that cannot derive a position from on-chain state alone and need a trusted party to submit position *coordinates* (never amounts), which the adapter then values live and re-verifies per read — so the feeder can only under-report. ether.fi's withdrawal queue is one such case: requesting a withdrawal burns eETH/weETH and mints a non-enumerable `WithdrawRequestNFT`, invisible to a pure-view NAV scan. Today `EtherFiWithdrawalQueueAssistedBalanceAdapter` tracks these via an **off-chain** `ASSISTANT_ROLE` agent that polls and submits the account's `tokenId`s — leaving a staleness window between the on-chain request and the agent's next submission, and depending on an off-chain process staying live.

The **wrapper-fed** approach (introduced for Nexus Mutual by ADR 0018) removes both: route the request/claim through a wrapper contract that pushes/pops the `requestId` into the adapter **atomically, in the same transaction**, with no off-chain component. This ADR adds a wrapper-fed adapter for ether.fi's withdrawal queue and captures the one way ether.fi differs materially from Nexus: **the claim is owner-only**.

### The ether.fi-specific constraint (why the claim is delegatecalled)

Verified against the live mainnet contracts:

- `LiquidityPool.requestWithdraw(address recipient, uint256 amount)` pulls `amount` eETH from `msg.sender` and mints the `WithdrawRequestNFT` **to `recipient`**.
- `WithdrawRequestNFT.claimWithdraw(uint256 tokenId)` does `require(ownerOf(tokenId) == msg.sender)`, **ignores ERC721 approvals**, burns the NFT and sends the ETH to `ownerOf`. `batchClaimWithdraw` has the same check; `seizeInvalidRequest` is `onlyOwner`. **There is no permissionless claim-on-behalf.**

For Nexus, `withdraw` is permissionless and routes funds to the NFT owner regardless of caller, so a `WRAPPER_ROLE` wrapper contract can `withdraw` with a normal CALL. ether.fi's owner-only claim rules that out: a wrapper contract can never be the NFT owner *and* the tracked account at once without either (a) owning every depositor's NFT (which breaks per-account ownership re-verification) or (b) being able to claim an NFT it does not own (which the protocol forbids). The resolution is to run the wrapper's logic **under delegatecall from the owning Safe** — then `msg.sender` seen by ether.fi is the Safe (the owner), and the ETH flows straight to it. The trade-off is that under delegatecall the wrapper's *own* storage/roles are the Safe's (so the wrapper cannot gate on its own roles, and cannot feed the adapter as itself in-line); we lean into it — the wrapper is a role-less delegatecall library, and it feeds the `WRAPPER_ROLE`-gated adapter by a regular call back to its own address (`SELF`, an immutable that survives delegatecall). For symmetry the deposit path is delegatecalled the same way.

## Decision

Make the ether.fi withdrawal-queue adapter **wrapper-fed**, **superseding** the earlier agent-fed adapter (which is removed). The wrapper-fed adapter keeps the name `EtherFiWithdrawalQueueAssistedBalanceAdapter` (it remains a member of the assisted family — the "assisted" label covers on-chain-wrapper feeders too) and is paired with `EtherFiWithdrawalQueueWrapper`. Same trust model and family invariant as ADR 0015 (cache coordinates only, value live, re-verify ownership per read → the feeder can only under-report), fed by an **on-chain contract holding `WRAPPER_ROLE`**, with an **incremental** single add/remove submit surface.

**Contracts.** Kept intentionally to **two self-contained contracts** for now (the family bases — `IWrapperFedBalanceAdapter` / `WrapperFedBalanceAdapter` / `WrapperFedNftCacheAdapter` / a valuation base — were tried and then **removed**; the shared abstractions will be re-extracted in a later PR, and reconciled with ADR 0018's wrapper-fed family when both land):

- **`EtherFiWithdrawalQueueAssistedBalanceAdapter`** — self-contained `AccessControl` + `IBalanceAdapter` + `IPositionDescribable` adapter. `DEFAULT_ADMIN_ROLE` administers `WRAPPER_ROLE`; constructor `(withdrawRequestNft, liquidityPool, underlyingToken, navCalculator, admin, wrapper)` with `wrapper` optional (granted after the wrapper is deployed, since the wrapper needs the adapter's address at construction). Holds its own `EnumerableSet.UintSet`-per-account id cache with `submit` / `remove` (both `onlyRole(WRAPPER_ROLE)`, so the wrapper is the sole mutator) plus an admin `clearAccount` rescue. `submit` verifies on every call that the id currently **belongs to** `account` (fail-loud `NotTokenOwner`; `TokenIdCacheFull` at the cap); `remove` requires the request to have been **claimed** — claiming burns the `WithdrawRequestNFT`, so a claimed id no longer exists — reverting `RequestNotClaimed` if it still exists. So the wrapper's `claimWithdraw` claims first (burning the NFT) and untracks **after**. Values each id live (position identity `etherfi` / `etherfi-withdrawal`, `finalized → getClaimableAmount` / `pending → min(amountOfEEth, amountForShare) − fee`). Reports the same positions the removed agent-fed adapter did; only the feeder and submit surface changed.
- **`EtherFiWithdrawalQueueWrapper`** — **delegatecall-only** logic (no roles of its own; it is not `AccessControl`). Both entrypoints are DELEGATECALLed by the owning Safe, so `msg.sender` seen by ether.fi is the Safe, and each feeds the adapter by a **regular call to the wrapper's own address** (`EtherFiWithdrawalQueueWrapper(SELF).submit`/`.remove`, where `SELF` is the wrapper's deploy address baked in as an immutable so it survives delegatecall) — so the adapter's `WRAPPER_ROLE`-gated mutators are invoked **by the wrapper**, never by the role-less Safe. Which Safe may run this is gated at the Safe layer (Zodiac Roles), not on the wrapper.
  - `requestWithdraw(amount)` — runs as the Safe: approves the LiquidityPool for the Safe's eETH and calls `LiquidityPool.requestWithdraw(recipient = address(this) = Safe, amount)` **directly**, so the eETH is pulled straight from the Safe and the NFT is minted to it, then `EtherFiWithdrawalQueueWrapper(SELF).submit(requestId)`.
  - `claimWithdraw(tokenId)` — runs as the Safe (== owner): `WithdrawRequestNFT.claimWithdraw(tokenId)` burns the NFT and sends the ETH to the Safe, **then** `EtherFiWithdrawalQueueWrapper(SELF).remove(tokenId)` untracks the now-claimed id (the adapter's `remove` requires the request to have been claimed).
  - A direct (non-delegatecall) call to either reverts `NotDelegateCall` — the `onlyDelegateCall` modifier (`address(this) == SELF` on a direct call).

## Consequences

- ether.fi withdrawals gain an on-chain, atomically-maintained tracking path. The earlier **agent-fed** ether.fi adapter (ADR 0014) is **removed** and superseded by this one; ADR 0014 still governs the StakeWise V3 exit-queue adapter, which remains agent-fed. StakeWise could gain a wrapper-fed variant later by the same pattern.
- The wrapper is **delegatecall-only for both entrypoints**, enforced by the `onlyDelegateCall` modifier (reverts `NotDelegateCall` on a direct call); karpatkey Zodiac Roles gates which Safe may delegatecall each. **EOA depositors cannot use the wrapper at all** (an EOA cannot delegatecall) — they interact with ether.fi directly; the intended depositors are Safe/Avatar accounts.
- `_safeMint` mints the `WithdrawRequestNFT` to the depositor Safe, which requires the Safe's fallback handler to implement `onERC721Received` (karpatkey Safes do; the assistant-fed adapter already assumes Safes hold these NFTs).
- `submit` requires the id to **belong to** `account` (revert `NotTokenOwner`); `remove` requires the request to have been **claimed** — the NFT burned — reverting `RequestNotClaimed` if it still exists. Consequently `claimWithdraw` claims first, then untracks the now-claimed id; if the claim reverts the whole tx rolls back atomically. Both mutators route through the wrapper via the `SELF` self-call so they are `WRAPPER_ROLE`-gated (the wrapper is the sole adapter mutator) — the delegatecalling Safe never needs a role on the adapter. An id that leaves the account **without** a claim (transferred away, so still exists) can't be `remove`d, but NAV stays correct regardless (reads re-verify ownership and value a non-owned id at 0); admin `clearAccount` is the cache-hygiene escape hatch.
- The wrapper-fed adapter remains a documented immutability exception (assisted family), expressed through `WRAPPER_ROLE`. The family invariant is unchanged, so the safety argument (feeder can only under-report) carries over verbatim.
- **Deploy/config wiring is deferred** to a follow-up (as ADR 0018 did for Nexus). When wired: deploy the adapter (`wrapper = address(0)`) → deploy the wrapper (needs the adapter address) → admin `grantRole(WRAPPER_ROLE, wrapper)` on the adapter → register the adapter on `NAVCalculator`. Which Safes may delegatecall the wrapper is configured at the Safe layer (Zodiac Roles), not on the wrapper.
- This ADR aligns with ADR 0018's wrapper-fed family. The shared `WrapperFed*` bases were intentionally NOT kept here (this adapter is self-contained for now); when PR #135 and this work both land, a shared wrapper-fed base should be extracted once and both adapters migrated onto it, and the family ADRs reconciled.
